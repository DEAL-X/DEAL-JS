# DEAL.JS (Declarative and Extensible Abstract Language for JavaScript) Compiler
**Bridging Humans, AI, and Machines through a Common Executable Language**
```
                               AI
                             ▲    ▲
                            /      \
                           /  DEAL  \
                          ▼          ▼
                      HUMAN ◄ ── ── ► MACHINE
```
**DEAL** (Declarative and Extensible Abstract Language) is an **AI-generatable**, **human-readable**, and **machine-executable** programming language designed to provide a common and reliable communication layer between **human intent**, **artificial intelligence**, and **target programming language**.

DEAL is a **declarative**, **abstract**, **deterministic**, **explicit**, **hybrid**, **interoperable**, **modular**, **extensible**, **consistent** and **reusable** programming language. Its fundamental grammar remains stable while domain-specific vocabulary, instructions, and localized terminology can be introduced through modules.

**The generated target programming language code will be the executable truth.**

**DEAL.JS** expresses computational intent using constrained, natural-language-like syntax while maintaining deterministic compilation and unrestricted interoperability with JavaScript. A DEAL.JS program can therefore be generated by AI, read and verified by humans, and deterministically translated into executable JavaScript.

DEAL.JS does not attempt to translate unrestricted natural language directly into executable programs. Instead, it defines a constrained grammatical language whose instructions have explicit compilation semantics, while allowing ordinary JavaScript to coexist freely within the same source.

Start with the [DEAL.JS quick-start guide](SAMPLE.md). The [samples](Samples/) are organized into [tests](Samples/tests/), [tutorials](Samples/tutorials/), and [practicals](Samples/practicals/). DEAL source is the primary format throughout; JavaScript snapshots are retained where useful as compiler expectations or results.


## Main principles
DEAL does not attempt to turn unrestricted natural language into executable programs. Instead, it defines a constrained and extensible grammatical language whose declarative instructions have deterministic JavaScript translations, while allowing ordinary JavaScript to remain embedded in the same source.
DEAL follows **five** main principles:
1. **Declarative** and **Abstract**: Every DEAL instruction expresses computational intent in a form resembling natural language.
    * Its syntax is designed around constrained English-like grammatical structures.
    * While retaining the precision required for deterministic compilation.
    * DEAL codes are readable as a simple Markdown document.
    ```md
    Use deal;
    # FillList
    Begin,

    ## ReadFile
        Begin,
            * MyFile = resource file open();
            * Log subject "Process started!";
            * If **MyFile** not be null, Begin:
                - The #Text be myFile content;
                - The successful be true;
                - End;
            * Else, Begin:
                - The text be empty;
                - The successful be false;
                - End;
        End;

    ## UseFile
        Try,
            * The list = text split "\n";
            * If list length be lesser than 1, Do:
                + ReadFile;
                + UseFile;
                + End;
            * Else Log success "Process finished successfully!";
        Catch err,
            * Log error "Could not finish the process because: " + err;
        Finally,
            * Log subject "Process finished!";

    End;
    ```
    * It will compile to the pure JavaScript code below:
    ```js
    // Used multiple libraries from "deal"
    (FillList = (() => {
        (ReadFile = (() => {
            MyFile = resource.file.open();
            Log.subject("Process started!");
            if (MyFile != null) {
                text = MyFile.content;
                successful = true;
            }  else {
                text = "";
                successful = false;
            }
        }))();
        (UseFile = (() => {
            try {
                list = text.split("\n");
                if (list.length < 1) {
                    ReadFile();
                    UseFile();
                }
                else Log.success("Process finished successfully!");
            } catch (err) {
                Log.error("Could not finish the process because: " + err);
            } finally {
                Log.subject("Process finished!");
            }
        }))();
    }))();
    ```
    * Also, the written DEAL code can be read as a simple document.
    * For example:
    ```ts
    For each url of the list, Load the url, then append all h3#title, to the destination;
    Otherwise log the error `Could not load the ${url}!`;
    ```
2. **Deterministic** and **Explicit**: Every DEAL instruction has a defined compilation into its destination language.
    * So the previous instructions will compile to the pure JavaScript code below:
    ```js
    for(const url of list) browser.open(url).then((data) => {
        handle(data);
        append(all("h3#title"), destination);
    }).catch((data) => {
        handle(data);
        log.error(`Could not load the ${url}!`);
    });
    ```
    * There is no hidden behavior.
    * Never runtime guessing.
3. **Hybrid** and **Interoperable**: Every DEAL instruction can coexist freely with its ordinary destination language code.
    * DEAL.JS does not replace JavaScript; it provides a higher-level instruction layer that interoperates with it.
    * DEAL.JS instructions and ordinary JavaScript coexist freely.
    * For example:
    ```ts
    for(const url of list)
        load url,
        then append(all("h3#title") to destination),
        Otherwise log the error `Could not load the ${url}!`;
    ```
    * Without any conflict.
4. **Modular** and **Extensible**: Every DEAL instruction can be extended through modules while its fundamental grammar remains stable.
    * It allows to become a shared vocabulary for different domains.
    * Modules can also provide alternative vocabularies for different natural languages (Spanish, German, ...).
    * For example:
    ```ts
    Use deal;
    use Scraper; // All libraries needed to scrape the web
    Use Spanish; // Contains all Spanish alternative reserved words.
    // ...
    Para cada url de la lista, carga la url, luego añade todos h3#title, al destino; 
    de lo contrario, registra el error `¡No se pudo cargar ${url}!`;
    ```
    * Then it will be exactly equal to the DEAL instructions below:
    ```ts
    use deal;
    use Scraper; // All libraries needed to scrape the web
    use Spanish; // Contains all Spanish alternative reserved words.
    // ...
    For each url of the lista, load the url, then append all h3#title, to the destino;
    otherwise log the error `¡No se pudo cargar ${url}!`;
    ```
5. **Consistent** and **Reusable**: Every DEAL instruction can explain its target programming language code for consistent reuse.
    * DEAL.JS can represent complex JavaScript behavior through reusable, higher-level instructions.
    * DEAL.JS can compile to the pure JavaScript code, for future reuse, everywhere the same.
    * Allowing implementations to be expressed once and reused through a human-readable vocabulary.
    * The generated JavaScript will be the executable truth.


## Main syntax
In the DEAL:
* All instruction based on four fundamental concepts:
    1. **Structures** define the grammar.
    2. **Commands** perform actions and functions.
    3. **Reserves** represent all reserved-words or noise-words defined for DEAL.
    4. **Handlers** of the workspace represent the current execution context.
* Predefined DEAL structures, commands, reserves and handlers allow for clearer, more human-readable, and more flexible procedures.
* A DEAL document can also be read as a simple Markdown document.
* Case statements of DEAL are very flexible (case-insensitive), instead of being somewhere:
    * Case-insensitive:
        * All target programming language ordinary structures, such as IF, FUNCTION, LET, etc.
        * All DEAL or third-party structures, such as BEGIN, USE, RESERVE, etc.
        * All DEAL or third-party commands, such as APPEND, COLLECT, POST, etc.
        * All DEAL or third-party reserveds, such as FROM, AND, WITH etc.
        * All DEAL or third-party handlers, such as BROWSER, WINDOW, DOCUMENT, etc.
            * Multiple of the most important interface variables, such as DOCUMENT, CONSOLE, SCREEN, etc.
            * Multiple of the most important interface functions, such as ALERT, CONFIRM, PROMPT, etc.
    * Case-sensitive:
        * All user-defined functions/variables/constants.
        * All objects' functions/variables/constants (almost everything is written after a dot('.')).
* To display code clearly, use `+`, `-`, or `*`, with just one space, before each line, similar to Markdown lists.
* Use single or double asterisks for highlighting in your code, similar to Markdown's italics or bolds.

*Note*: To keep your code more readable and avoid conflicts with DEAL, you should not use `"use strict";` phrase anywhere.
* Because in the strict mode, using a variable without declaring it will not be allowed, then it makes it difficult for the DEAL code writer to use some instructions.

### Structures
Instead of supporting all JS structures, DEAL engine contains some special structures.
* Built into the compiler.
* They define the grammar and cannot be overridden (IF, FOR, COMMAND, USE, RESERVE, WILL, BEGIN, DOING, etc.)
* Multiple of the most important DEAL Structures are:

#### Definition
* To define constant or variables:
    ```ts
    Consider const constant is procedure;
    Consider var variable is equal procedure;
    Consider let letVariable be procedure;
    Consider directVariable equals procedure;
    ```
    They will compile to:
    ```js
    const constant = js-procedure;
    var variable = js-procedure;
    let letVariable = js-procedure;
    let directVariable = js-procedure;
    ```
* Pure JS definition structures are available as the same.

#### Conditions
* To work in a special conditions
    ```ts
    If condition, procedure; Else procedure;
    ```
    It will compile to:
    ```js
    if(js-condition)
        js-procedure;
    else 
        js-procedure;
    ```
* All other JavaScript conditional structures (such as switch/case, ternary) are available as the same.

#### Iterations
* Working with a collection based iterations
    ```ts
    For item of/in collection/object, procedure;
    ```
    ```ts
    For each item of/in collection/object, procedure;
    ```
    All of them will compile to:
    ```js
    for(js-item of js-collection)
        js-procedure;
    ```
    or
    ```js
    for(js-item in js-object)
        js-procedure;
    ```
* Using a conditional iterations
    ```ts
    While condition, procedure;
    ```
    It will compile to:
    ```js
    while(js-condition)
        js-procedure;
    ```
* Using a post conditional iterations
    ```ts
    Do { procedures } while condition;
    ```
    It will compile to:
    ```js
    do {
        js-procedures
    } while(js-condition);
    ```
    Also you can use a modern approach:
    ```ts
    # doingTask procedure; WHILE condition, doingTask;
    ```
    It will compile to:
    ```js
    (doingTask = (() => js-procedure))();
    while(js-condition) doingTask();
    ```

#### Blocks
* To make a DEAL procedures-block
    ```ts
    Begin procedures End;
    ```
    ```ts
    Do procedures End;
    ```
    They will compile to:
    ```js
    {
        js-procedures
    }
    ```
* To make a DEAL callable procedures-block
    ```ts
    Doing procedures End;
    ```
    It will compile to:
    ```js
    () => {
        js-procedures
    };
    ```
* To make a tryable block
    ```ts
    Try procedures; Catch problem, procedure; Finally procedure;
    ```
    It will compile to:
    ```js
    try {
        js-procedures
    } catch (problem) {
        js-procedures
    } finally {
        js-procedures
    }
    ```

#### Asynchronous blocks
* To have a multi-thread program, you can make and manage promises
    ```ts
    Will procedure then procedure; otherwise procedure; anyway procedure;
    ```
    It will compile to:7
    ```js
    new Promise((resolve, reject)=>js-procedure)
        .then((data)=>js-procedure)
        .catch((data)=>js-procedure)
        .finally((data)=>js-procedure)
    ```

#### Collections
* To filter collections
    ```ts
    array Where condition
    ```
    It will compile to:
    ```js
    js-array.filter(data=>js-condition)
    ```
* To sort collections
    ```ts
    array Order by key1, key2
    ```
    It will compile to:
    ```js
    js-array
        .sort((a, b)=>(a,b)=>a.js-key1>b.js-key1?1:a.js-key1==b.js-key1?0:-1)
        .sort((a, b)=>(a,b)=>a.js-key2>b.js-key2?1:a.js-key2==b.js-key2?0:-1)
    ```
* To slice collections
    ```ts
    array Limit number, count
    ```
    It will compile to:
    ```js
    js-array.slice(js-number, js-count)
    ```
    ...

### Commands
All commands represent executable operations.
* That are case-insensitive.
* Can be overridden in code.
* A very small set that the compiler itself needs for parsing or semantic analysis defined built in.
* They will include the following cases:
    * All simple DEAL built-in commands.
    * All third-party commands (you add them to your instructions using the USE statement).
    * All user-defined commands (You defined using the COMMAND statement).
* The user-defined command will be accessible exactly like other global commands, too.
* They can define in four ways:
    * Action
    * Function
    * Definition
    * Delegation

#### Action commands
* By action command there will make a simple callable, but with these features:
    * All action commands must be defined globally.
    * They will have a special case-insensitive COMMANDNAME.
    * They will call immediately after definition once.
    * Will be able to call again, just using the name without any parentesis.
* To define a special action command, use 1-6 `#` signs followed by at least one space before the action `COMMANDNAME`.
    ```ts
    # COMMANDNAME procedure;
    ```
    or
    ```ts
    ### COMMANDNAME procedure;
    ```
    or
    ```ts
    ## COMMANDNAME: procedure;
    ```
    They will compile to:
    ```js
    (COMMANDNAME = (() => js-procedure))();
    ```
* Then can call it case-insensitively, with or without parenthesis:
    ```ts
    commandName
    ```
    It will compile to:
    ```js
    COMMANDNAME()
    ```

#### Function commands
* Every function command behaves like a JavaScript function while following several conventions:
    * All function commands must be defined globally.
    * They will have a special case-insensitive COMMANDNAME.
    * All inputs of each command should be optional. So ensure every parameter has a default value.
    * If the command has no returned output, it can return itself (specially when there is not inputted arguments). 
* The main syntax to define a special function commands:
    ```ts
    Command COMMANDNAME(input1=value1, ...) {	// All inputs of each command must have a default value
        procedures
        /*
            // Should return one of the following
            return output;
            return COMMANDNAME; // If you don't have any return value, you should return the command directly (usually when you do not have input arguments).
            // It will be useful when  you want to send a callable version of the command to another one as an input
        */
    }
    ```
    It will compile to:
    ```js
    function COMMANDNAME(input1=value1, ...) {
        js-procedures
    }
    ```
* Four ways to call a command:
    * Grammatical:			
        ```ts
        CommandName                            		    // To call without any inputted arguments
        ```
    * Functional:			
        ```ts
        commandName(val1_1, CMD2(val2_1, val2_2))		// Exact calling a function
        ```
    * Procedural:			
        ```ts
        commandname val1_1, CMD2 val2_1, val2_2	        // Separated by comma.
        ```
    * Optional:			
        ```ts
        commandname ...{								// Sending an object of named values
            inp1_1: val1_1,
            inp1_2: commandname2 { inp2_1: val2_1, inp2_2: val2_2 } 
        }
        ```
* You can combine the methods above, depending on your code situations.
* All of the ways will convert to a simple function call.

#### Definition commands
* Every definition command behaves like a JavaScript object while following several conventions:
    * All definition commands must be defined globally.
    * They will have a special case-insensitive COMMANDNAME.
* The main syntax to define a special definition commands:
    ```ts
    Command COMMANDNAME = {
        propertykey1 : propertyValue1,
        propertykey2 : propertyValue2,
        /* Exactly same to an object... */
    };
    ```
    It will compile to:
    ```js
    var COMMANDNAME = {
        js-propertykey1 : js-propertyValue1,
        js-propertykey2 : js-propertyValue2,
        /* Exactly same to an object... */
    };
    ```
* Then to use:
    ```ts
    commandName propertykey1
    ```
    It will compile to:
    ```js
    COMMANDNAME.js-propertykey1
    ```

#### Delegation commands
* The simplest but valuable type of commands.
* Every delegation command behaves like a simple JavaScript variable while following several conventions:
    * All delegation commands must be defined globally.
    * They will have a special case-insensitive COMMANDNAME.
    * All words, after being used only one time, a stuck acceptor sign `#keyword`, or wrapping word between sticked single or double asterisks `*keyword*`, will convert to a delegation command.
    * They can convert everything (constant, variable, function, class, etc.), even after their definition.
    * They will not change the behavior of the converted thing.
 * The main syntax to make then call a special delegation commands is:
    ```ts
    var test1Var = "The test value number 1";
    console.log(test1Var); // You should use case-sensitively
    console.log(#test1Var); // You should use case-sensitively (But made it case-insensitive after a wrapping by sticked asterisks)
    console.log(TEST1var); // Its a delegation command and is case-insensitive now
        
    var #test2Var = "The test value number 2"; // You can define everything case-insensitive the first time using a sticked acceptor sign `#`
    console.log(Test2VAR); // Its a delegation command and is case-insensitive now
    ```
    It will compile to:
    ```js
    var test1Var = "The test value number 1";
    console.log(test1Var);
    console.log(test1Var);
    console.log(test1Var);
        
    var test2Var = "The test value number 2";
    console.log(test2Var);
    ```
* The type of each keyword can also be specified using `:commandType` next to use a delegation command, for instance:
    ```ts
    var #test1Var:string = "The test value number 1"; // Can define the identifier's type at definition time
    console.log(test1Var);

    var test2Var = "The test value number 2";
    console.log(#test2Var:string); // Can define the identifier's type everywhere if it does not define before
    ```
    It will compile to:
    ```js
    var test1Var = "The test value number 1";
    console.log(test1Var);
        
    var test2Var = "The test value number 2";
    console.log(test2Var);
    ```
* The force type of the subsequent word for each command can also be specified using `:commandType:nextType` or `::nextType` following a delegation command.
    ```ts
    var #test1Var:int:string = 4;
    list insert test1Var, www.mimfa.net; // the test1Var subsequent word will convert to string

    var #test2Var::string = 5;
    list insert test2Var, www.deal.mimfa.net; // the test2Var subsequent word will convert to string
    ```
    It will compile to:
    ```js
    var test1Var = 4;
    list.insert(test1Var, "www.mimfa.net"); // the test1Var subsequent word will convert to string
    var test2Var = 5;
    list.insert(test2Var, "www.deal.mimfa.net"); // the test2Var subsequent word will convert to string
    ```

### Reserves
DEAL allows optional readability words that improve the natural flow of the language. They will affect only the parser and contain no JavaScript code. These can be one of two groups below:
* Reserved words: All words will be replaced directly in the script while being preserved in the source code.
    * The user can call any one of the codes below freely.
    * The reserved name will be completely case-insensitive.
    * It can improve the readability of the code with a predefined replacement for them.
    * You can add a reserved-word to the parser using the following syntax:
        ```ts
        Reserve reservedWordName as "replacement";       // This line affects only the parser, and will replace the used reservedWordName by replacement everywhere it used.
        ```
    * For example, you can write any one of the bellow codes, without any effects in meaning:
        ```ts
        Reserve into as ",";
        // Other procedures
        Save "hello world!" into "index.html";
        // With the same meaning
        Save "hello world!" , "index.html";
        ```
        Or:
        ```ts
        Reserve restart as "browser.open(\"http://mimfa.net\");";
        // Other procedures
        Restart
        // With the same meaning
        browser.open("http://mimfa.net");
        ```
    * Parser will replace those specified words before parsing by default.
* Noise-words: All words are ignored semantically while being preserved in the source code.
    * The user can call any one of the codes below freely.
    * The reserved name will be completely case-insensitive.
    * It can improve the readability of the code without carrying any semantic meaning on them.
    * You can add a noise word to the parser using the following syntax:
        ```ts
        Reserve noiseWordName;       // This line affects only the parser, not JavaScript.
        ```
    * For example, you can write any one of the bellow codes, without any effects in meaning:
        ```ts
        Reserve the;
        // Other procedures
        Click all the #nextbutton
        // With the same meaning
        Click all #nextbutton
        ```
        Or:
        ```ts
        Reserve a;
        // Other procedures
        browser.open("www.example.com")
        // With the same meaning
        browser.open("www.example.com")
        ```
    * Parser will skip those specified words before parsing by default.

### Native web runtime

DEAL.JS separates HTTP transport from browser-page control. The same web library can be used by a ClearScript host without pretending that the host has a native browser DOM.

#### HTTP requests

The JavaScript `fetch` compatibility layer converts request bodies to bytes, transfers binary data through Base64, and converts the native response into a JavaScript `Response`.

```deal
Consider response constant be await fetch "https://example.com/data", {
    method: "GET",
    headers: { "Accept": "application/json" },
    timeout: 15000
};

If response ok is not true, throw new Error "HTTP " + response.status;

Consider data constant be await response.json();
```

It compiles to ordinary JavaScript:

```javascript
const response = await fetch("https://example.com/data", {
    method: "GET",
    headers: { "Accept": "application/json" },
    timeout: 15000
});

if (response.ok != true)
    throw new Error("HTTP " + response.status);

const data = await response.json();
```

The host transport supports HTTP and HTTPS, common request methods, request and response headers, byte-safe request and response bodies, redirects, request timeouts, cancellation, and a host cookie jar. `credentials: "omit"` disables cookie sending and storage for that request. Because the host has no browser-origin context, `same-origin` and `include` both use the host cookie jar.
The common object hierarchy is:

- `BROWSER`: the `Browser` provider.
- `BROWSER.Driver`: the selected browser driver.
- `BROWSER.Session`: the active protocol-neutral browser session.
- `BROWSER.Tab`: the currently displayed tab in the provider's browser session.
- `BROWSER.Tabs`: the synchronous `BrowserTabs` collection of `BrowserTab` handles; `BROWSER.Tabs.Current` resolves the current tab.
- `BROWSER.Tab.Window`: the remote Window proxy.
- `BROWSER.Tab.Windows`: the child-frame collection.
- `BROWSER.Downloads`, `BROWSER.Permissions`, and `BROWSER.Runtime`: optional browser-level services.

`WindowId` exposes the native application-window identifier when the selected backend provides one; Firefox uses BiDi browsing-context IDs and therefore reports `null` for this Chromium-specific concept. `Cookies.Document` is based on the standard `document.cookie` API; `Cookies.All` uses the Chromium CDP cookie command and is not available through Firefox.

A `BrowserTab` exposes synchronous `Id`, `Url`, `Title`, `Window`, and `Windows` properties. Its common navigation and history methods include `Load`, `Navigate`, `Reload`, `Back`, `Forward`, `Go`, `Locate`, and `Relocate`. Browser-level operations are `Open`, `Activate`, and `Close`. The current tab can also be closed with `browser.Tab.Close()`.

The Window proxy exposes `Document`, `Location`, `History`, `Navigator`, `Screen`, `Console`, `Cookies`, and `Storage`. Their public properties are PascalCase. Examples include:

- `Document.Title`, `Document.Url`, `Document.Html`, `Document.Text`, `Document.ReadyState`, and `Document.VisibilityState`.
- `Location.Href`, `Origin`, `Pathname`, `Search`, and `Hash`.
- `History.Length` and `State`.
- `Navigator.UserAgent`, `Language`, `Languages`, `Platform`, `Online`, and `CookieEnabled`.
- `Screen.Width`, `Height`, `AvailWidth`, `AvailHeight`, and `ColorDepth`.
- `Storage.Local` and `Storage.Session`; each storage area exposes `Length` and `Keys`.

Browser properties return native values synchronously. The non-`Async` convenience methods are synchronous as well; explicitly named `...Async()` counterparts remain awaitable. DEAL source uses familiar lower-case browser-object spelling because ClearScript resolves the public PascalCase .NET members without regard to casing:

```ts
Consider tab is browser open https://example.com/;
Consider title is browser tab window document title;

browser tab window storage local setItem("key", "value");
Consider value is browser tab window storage local getItem("key");

go https://example.org/;
browser tab back();
```

The File System Access API is accessed through the browser's native file pickers. Availability depends on the browser, its secure-context rules, permissions, and user-activation requirements. The `Open` and `Save` operations return remote handles; their explicit `...Async()` counterparts remain available.

Downloads, permission overrides, browser command-line information, and other vendor-specific operations are optional capabilities. The Chromium drivers provide the existing CDP-backed services. A driver that does not implement a capability, including Firefox for the current Chromium-only services, reports `NotSupportedException` rather than silently sending a CDP command.

The native browser test is [Browser-Driver-Smoke-Test.js](Samples/tests/runtime/Browser-Driver-Smoke-Test.js); run it once with each driver configured by the .NET host. The Chromium-specific file-picker checks remain in [Browser-Object-Model-Smoke-Test.js](Samples/tests/runtime/Browser-Object-Model-Smoke-Test.js). Fetch and local-file checks are in [Native-Web-Smoke-Test.js](Samples/tests/runtime/Native-Web-Smoke-Test.js).

#### Current-tab tracking and closing

The provider does not assume that the first item returned by a protocol is the active tab, and it does not treat an arbitrary available tab as the current tab. Reading `browser.Tab` resolves the page the browser currently displays. Chromium uses the page visibility state reported through CDP; Firefox uses WebDriver BiDi browsing contexts and the same page visibility state. Browser UI tab switches are reflected the next time `browser.Tab` is accessed.

When `browser.Tab.Close()` closes the current tab, the provider waits for the closed context to disappear and updates its current-tab reference to the remaining visible page. If the browser reports no visible page, it falls back to the adjacent tab. Closing the last tab creates a replacement blank tab so the provider remains usable.

#### Address resolution and local files

The shared `Router` normalizes incomplete web addresses and resolves local paths. Browser navigation, Fetch, the legacy `Send` request helper, and remote `USE`/`REUSE` module resolution use the same provider.

```javascript
browser.tab.load("./Samples/tests/fixtures/Local-Page-Smoke-Test.html");

Consider response is await fetch("./Samples/tests/fixtures/Local-Page-Smoke-Test.html");
Consider html is await response.text();
```

The selected browser loads local files through `file://` and applies its normal security restrictions. Host Fetch supports local-file `GET` and `HEAD` requests, returns status `200`, an absolute `file://` response URL, an inferred content type, and the file bytes. Missing files reject the Fetch promise. Local file reads do not use HTTP cookies or HTTP request headers.

#### USE and REUSE

`USE` and `REUSE` are compile-time dependency-loading instructions:

```deal
Use deal/core;
Use deal/web;
Use ./Libraries/Selectors;

// The dependency is already loaded, so this does not process it again.
Use ./Libraries/Selectors;

// Force the same dependency to be processed again.
Reuse ./Libraries/Selectors;
Reuse https://example.com/lib.djs;
```

Both instructions resolve resources through the compiler's shared path and resource resolution. `USE` skips a dependency already registered by the current compiler; `REUSE` forces that dependency to be processed again. `REUSE` does not imply a separate download or cache-refresh policy for remote modules.
